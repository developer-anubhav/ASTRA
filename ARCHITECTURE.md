# ASTRA & CORTEX — Architectural Specification

## 1. Product Identity & Core Mission

**ASTRA** is a web-first Global Intelligence and Situational Awareness Platform engineered to consolidate, normalize, and visualize global geospatial and telemetry data across four primary operational domains:
1. **Maritime** (AIS vessel telemetry, hull metrics, navigation vectors)
2. **Airspace** (ADS-B / Mode S airframe tracking, altitude fixes, squawk monitoring)
3. **Space** (Keplerian orbital elements, satellite catalogs, SGP4/SDP4 propagation)
4. **Global Events** (Verified geopolitical, environmental, and security intelligence dispatches)

**CORTEX** is the integrated AI reasoning assistant. Embedded throughout the console, CORTEX interprets multi-domain telemetry, explains anomalies, assists cross-domain correlation, and delivers structured findings with traceable provenance citations.

> Canonical product taglines:
> - **ASTRA**: *See the world. Understand the signals.*
> - **CORTEX**: *Intelligence beyond information.*

### 2.1 Service Interfaces
All domains implement typed TypeScript contracts in `src/services/interfaces.ts`:
- `MaritimeService`: `getVessels()`, `getVesselById()`
- `AviationService`: `getAircraft()`, `getAircraftById()`
- `SpaceService`: `getSatellites()`, `getSatelliteById()`
- `EventsService`: `getEvents()`, `getEventById()`
- `SourcesService`: `getSources()`, `getSourceById()`
- `AnalyticsService`: `getOverview()`
- `AssistantService`: `query()`

UI components never query mock data directly; they consume the service registry exported at `@/services`. Swapping from demonstration mode to real live providers requires changing the adapter instantiation in `src/services/index.ts` without touching any UI component.

## 3. Data Provenance & Integrity Conventions

Every entity in ASTRA is tagged with an immutable provenance taxonomy:

| Provenance Level | Description | Visual Classification |
|---|---|---|
| `live` | Directly received telemetry from an active sensor station (e.g., coastal AIS receiver, Mode S ground station). | Green pulse badge |
| `cached` | Validated historical observation retained within the cache validity window. | Amber badge |
| `propagated` | Mathematical extrapolation from orbital elements (e.g., SGP4 satellite trajectory from a TLE epoch). | Blue badge |
| `inferred` | Analytical deductions or algorithmic correlations generated by CORTEX or intelligence models. | Purple outline / disclaimer |
| `demonstration` | Synthetic demonstration records created strictly for interface evaluation. | Violet DEMO banner |

### Integrity Rules
1. **No Fabricated Real-Time Claims**: If satellite coordinates are computed from orbital elements, they are explicitly tagged as `propagated` with the associated Keplerian epoch. They are never labeled as radar or optical sensor locks.
2. **Factual Separation**: In the Global Events domain, news dispatches distinguish `reported` (single-source unconfirmed), `corroborated` (multi-source verified), `official` (governmental release), and `disputed`. Analytical inferences are rendered in isolated warning containers.

## 4. Privacy & Zero-Retention Architecture

ASTRA is built from the ground up as an anonymous-by-design intelligence console:
- **No User Accounts or Authentication**: No login forms, JWT session cookies, or user profiling.
- **Zero Persistent Conversation Storage**: CORTEX interactions are held strictly in ephemeral React memory. Navigating away or refreshing the tab permanently purges the chat history.
- **Zero Third-Party Trackers**: No Google Analytics, Facebook Pixel, or telemetry trackers.
- **Client Credential Isolation**: The frontend contains zero API keys or service tokens. External provider requests route through server-side proxies or backend microservices.

## 5. Planned Backend & Database Integration

### 5.1 Technology Stack
- **Backend**: Python 3.12+ with FastAPI, Pydantic v2, and async SQLAlchemy / asyncpg.
- **Geospatial Database**: PostgreSQL 16 with PostGIS 3.4 for spatial indexing (R-Tree, GiST).
- **Cache & Pub/Sub**: Redis for real-time telemetry deduplication and WebSocket event fanout.

### 5.2 Planned REST Endpoints
- `GET /api/v1/maritime` — Ingested AIS vessel telemetry filtered by bounding box and vessel type.
- `GET /api/v1/aircraft` — ADS-B state vectors from ground station collectors.
- `GET /api/v1/satellites` — NORAD TLE catalog with on-the-fly SGP4 orbit propagation.
- `GET /api/v1/events` — Verified intelligence feeds filtered by severity, geography, and date range.
- `GET /api/v1/sources` — Health status, API credit consumption, and ingestion latency per provider.
- `GET /api/v1/analytics/overview` — Aggregated counts and spatial statistics.
- `POST /api/v1/assistant/query` — CORTEX reasoning endpoint (orchestrating retrieval-augmented intelligence reasoning).

## 6. Provider Integration Guide

To connect live data providers in production:

### 1. OpenSky Network (Aviation)
- Register for an institutional or research account at [opensky-network.org](https://opensky-network.org).
- Implement `LiveAviationAdapter` calling `/api/states/all` with bounding box coordinates.
- Respect the 400 credit/day anonymous rate limit or 1000 credit/day authenticated tier.

### 2. CelesTrak (Space / Satellites)
- Fetch active orbital element sets from `https://celestrak.org/NORAD/elements/gp.php?GROUP=active&FORMAT=tle`.
- Use a server-side SGP4 library (`sgp4` in Python) to compute sub-satellite points at current UTC.
- Retain the original element epoch timestamp for every propagated record.

### 3. Maritime AIS (Spire, AISHub, or Global Fishing Watch)
- Secure an AIS data license compliant with commercial or non-profit requirements.
- Connect an NMEA/JSON WebSocket stream for high-frequency vessel updates into PostGIS.
- Ensure terrestrial vs satellite AIS limitations are displayed to operators.
